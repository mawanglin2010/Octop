# 内容团队：从线索到公众号草稿

用五位专家组成一支内容团队，把“话题 → 公众号文章”这条线拆成有据可查的五站，每一站都能单独使用：

| 站 | 专家 | 做什么 |
|----|------|--------|
| 1 采集 | 内容采集员 `content-scout` | 找线索，登记来源，逐字摘录，标可信度，输出线索包 |
| 2 撰写 | 公众号写作专家 `wechat-writer` | 按线索包写稿，事实句带来源编号 |
| 3 核验 | 内容核验员 `fact-checker` | 事实溯源、原创性、合规、格式，给通过 / 需修改 / 不通过 |
| 4 配图 | 推文配图专家 `article-illustrator` | 搜索授权清楚的图或用生图模型生成，登记配图单，导出预览 PDF |
| 5 发布 | 发布专员 `article-publisher` | 用户看过预览并确认后，存入公众号草稿箱，记台账 |

五位专家都随安装包自带，不依赖线上专家市场。另有「共享文件夹管理员」`shared-folder-keeper` 负责查看和清理共享文件夹（见第 6 节）。

**一题一篇**：用户一次给了几个热点或主题，每个热点、每个主题各建一个文章包，各走一遍五站，各出一篇文章和一份预览 PDF，不合并成一篇“热点汇总”。这样每篇都能写深。

## 1. 交接：文章包

团队成员各有独立工作区，互相看不到对方的文件。每一站都把成果写进同一份文本“文章包”，交接靠两条路：

- **共享文件夹**：同一用户的所有专家共用一个共享文件夹（Octop 主机上的 `~/.octop/users/<用户名>/shared/`）。每站做完用 `shared_file_put` 把文章包放进去（共享名 `<话题>/文章包.md`），下一站用 `shared_file_get` 取回。图片、PDF 这类文件只能这样交接；
- **回复里的文字**：关键内容（线索包、初稿、核验报告、配图单）同时贴在回复里，主持人能看到并转述。

```
选题单 → 线索包 → 初稿 → 核验报告 → 配图单 → 发布单
         采集员   写作专家  核验员    配图专家   发布专员
```

- **线索包**：每条来源有编号（S1、S2…）、网址、发布方、发布日期、抓取时间、可信度（A–D）、状态（可用 / 存疑 / 不可用）和**逐字摘录**。
- **初稿**：每个带事实的句子句末标来源编号，如 `[S1]`；由来源数字推算的句子加 `[推算]`。
- **核验报告**：记录结论、被核验初稿的哈希、轮次、分项结果、问题清单。初稿改过一个字，哈希就变，报告随即作废。
- **配图单**：配图专家登记每张图的位置（封面、开头、第几段后、哪个小标题后）、方式（搜索 / 生成）、文件和共享名、文件哈希、图注，以及搜索图的网址、来源页、署名、授权或生成图的提示词、模型；每张图还要写明用途（点题 / 衔接 / 说明）、画面要点、依据（初稿原句）、画面元素和看图后的画面描述，配图专家的脚本会核对依据是不是原文、元素是不是文中出现过、衔接图有没有同时照顾上文和下文。**配图不改初稿**，预览和发布时才插进正文，所以核验报告不会因为配图而过期；生成的图图注自动带“（AI 生成）”。
- **发布单**：发布专员写入平台、状态、media_id、时间。

五位专家各带一份相同的 `article_pack.py`（有测试保证内容一致），可以建包、批量建包、读写各节、算哈希、校验结构、做发布前把关：

```bash
python article_pack.py new 文章包.md --topic "话题" --audience "读者" --length "1000 字"
python article_pack.py batch outputs/pack --topic "热点一" --topic "热点二"   # 每个话题一个文章包
python article_pack.py validate 文章包.md
python article_pack.py gate 文章包.md --for publish [--confirmed]
```

## 2. 建团队

1. 在“专家”页面，用模板分别创建五位专家：内容采集员、公众号写作专家、内容核验员、推文配图专家、发布专员。
2. 打开“我的团队”，新建团队，成员选这五位。主持人只负责分派，不会自己干活。
3. 团队创建后启动它，打开团队的“工作区”，把下面这段“团队准则”**追加**到主持人 `AGENTS.md` 的末尾，让主持人按这个流程派工；改完重启一次团队。

### 团队准则（可直接粘贴）

打开团队的工作区，把下面的内容**追加到主持人 `AGENTS.md` 的末尾**（保留原有内容，原有的是主持人的基本规矩）。只复制围栏里面的内容。

````markdown
## 内容团队流程

本团队固定五位成员，按“采集 → 撰写 → 核验 → 配图 → 发布”接力：

| 成员 | 职责 |
|------|------|
| 内容采集员 | 找线索，输出带出处的线索包 |
| 公众号写作专家 | 按线索包写稿，事实句带来源编号 |
| 内容核验员 | 核验稿子，给出通过 / 需修改 / 不通过 |
| 推文配图专家 | 给核验通过的稿子配封面和插图，导出预览 PDF |
| 发布专员 | 把用户确认过的稿子存入公众号草稿箱 |

成员的工作区互相看不见。文章包和图片放在共享文件夹里交接（共享名 `<话题>/文章包.md`），**每次派工都要写明共享名，并把需要的文字完整放进派工消息里**。

**一题一篇**：用户给了几个热点或主题，就当成几篇独立的文章，每篇单独走完下面的流程（可以并行派工），不要合并成一篇。

### 流程

1. **问清需求**：用户给出话题后，先问清读者、平台、篇幅、禁区；缺了就问一句。
2. **派内容采集员**：写成任务说明书（话题、范围、时间窗口、读者、禁区），并要求“线索包全文放在回复里”。多个话题要求采集员每个话题各建一个文章包、分别交付，可以一轮里并行派工。
3. **派公众号写作专家**：把采集员回复里的线索包全文放进派工消息，并要求：
   - 每个事实句带来源编号，如 `[S1]`；
   - 不引用状态为“不可用”的来源；
   - “存疑”来源必须用“有网友反映”“据称”这类限定语；
   - 初稿全文放在回复里。
4. **派内容核验员**：把线索包和初稿一起放进派工消息。
5. **按核验结论处理**：
   - **通过**：派推文配图专家，给它文章包的共享名，要求封面 1 张（点题）、正文 2–4 张（优先放在两节之间做衔接），每张写明用途和依据的原句，导出预览 PDF，配图单全文放在回复里；
   - **需修改**：把核验报告里“必须处理”的条目原文转给公众号写作专家修改，改完再交内容核验员重新核验；缺来源的问题转给内容采集员补充；最多往返两轮；
   - **不通过**：向用户说明原因，建议重新采集或放弃这个选题；
   - **两轮后仍有必须处理的问题**：不再往返，把剩余问题告诉用户，由用户决定。
6. **请用户确认**：向用户汇报核验结论、配图情况和预览 PDF 的位置，请用户先看 PDF，再问“是否存入公众号草稿箱”。用户对配图有意见就回到配图专家修改。用户明确同意之后，才把文章包的共享名派给发布专员。
7. **收口**：发布专员从共享文件夹取回文章包和配图，只存草稿。提醒用户到公众号后台预览，自己点发布。

### 铁律

- 没有核验通过、或核验之后改过任何一个字的稿子，**不得**派给配图专家和发布专员；
- 用户没有看过预览、没有明确同意，**不得**派发布；
- 几个热点或主题**不得**合并成一篇。
````

## 3. 一次完整的对话

```
用户   ▶ 帮我写一篇关于“示例市充电桩补贴”的公众号文章，读者是想建桩的商户，1000 字左右。
主持人 ▶ 好的，我先让采集员收集线索。（派内容采集员）
采集员 ▶ 收集到 4 条来源（A×1，B×1，C×1，D×1），D 级传言已列为不可用；线索包全文如下……
主持人 ▶ （把线索包放进派工消息，派公众号写作专家）
写作员 ▶ 初稿如下，事实句均标了来源编号，一处推算已标 [推算]……
主持人 ▶ （把线索包和初稿派给内容核验员）
核验员 ▶ 结论：需修改。必须处理 2 条：①第 2 段数字对不上 S1……
主持人 ▶ （把两条问题派给写作专家）…… 第二轮核验：通过。
主持人 ▶ （把共享名派给推文配图专家）
配图员 ▶ 封面 1 张（生成，已标 AI 生成），正文 2 张（1 张发改委官网发布图，1 张生成）；预览 PDF：outputs/preview/示例市充电桩补贴.pdf；配图单如下……
主持人 ▶ 核验已通过，配图和预览 PDF 已生成，请先看一下 PDF。要存入公众号草稿箱吗？
用户   ▶ 存吧。
发布员 ▶ 已取回 3 张配图，哈希一致；已存入草稿箱（media_id …）。只存了草稿，请到后台预览后自己发布。
```

## 4. 公众号接口的准备

发布专员通过公众号接口把文章存入草稿箱，需要：

1. 公众号后台“设置与开发 → 基本配置”里的 AppID 和 AppSecret；
2. 把运行 Octop 的机器的出口 IP 加到后台的 IP 白名单；
3. 账号有草稿箱相关接口的权限（**未认证的个人订阅号通常没有**，这时发布专员会改为导出 HTML，由你手动粘贴）；
4. 凭据只放环境变量 `WECHAT_APP_ID`、`WECHAT_APP_SECRET`，让专家用 `write_env_file` 写入 `.env`，不要贴在对话里。

接口的调用细节和错误码处理见发布专员的 `wechat-draft/references/wechat-api.md`。接口按微信开放文档编写，没有用真实公众号验证过。

## 5. 能做到什么，做不到什么

- **核验能证明**：稿子里的数字、日期、引语和线索包摘录是否一致；链接是否可打开；有没有命中违规关键词；格式是否符合平台限制；逐字搬运的比例。
- **核验不能证明**：来源本身是真的；摘录忠实于来源页面；没有数字、日期、引语的纯观点性断言是否有依据（这部分靠核验员人工复核）。
- **脚本只认阿拉伯数字**，“三百万”这类中文数字不识别。
- **流程由主持人模型推进**，团队准则和文章包的校验把最关键的几步变成了可检查的卡点，但不是写死的流程引擎；重启后在途任务会丢。
- **采集依赖搜索服务**：需要在设置里配置至少一个搜索服务（如 Tavily、Brave）；没配置时只能用网页抓取。
- 其他平台（小红书、头条等）没有稳定的官方接口，发布专员只导出可复制的文本。

## 6. 共享文件夹与清理

- 共享文件夹按用户隔离：同一用户的专家都能读写，别的用户看不到；在每位专家的“工具”设置里属于“共享文件夹”分组，可以单独关掉；
- 工具：`shared_file_put`（放入）、`shared_file_get`（取到自己的工作区，默认 `shared/<共享名>`）、`shared_file_list`（列出）、`shared_file_delete`（删除，只在用户要求时用）；
- 共享文件夹**不会自动清理**。用「共享文件夹管理员」查看占用、挑出很久没动的文件，确认后删除；删除用户时，这个用户的共享文件夹会一起删掉。

## 7. 预览 PDF

- 配图专家用 `preview_pdf.py` 把初稿和配图排成公众号样式，导出 `outputs/preview/<话题>.pdf`，同时生成同名 `.html`；页首标“预览稿，未发布”和核验结论，文末列参考来源、图片来源和配图清单；
- PDF 由无头 Chromium 打印，需要在 Octop 设置 → 浏览器里安装 Chromium；没装时只生成 HTML，用浏览器打开即可预览；
- 机器上没有中文字体时 PDF 里的中文会显示成方框（飞牛等精简系统可能遇到），可安装 `fonts-noto-cjk` 或文泉驿字体；HTML 版不受影响。

## 8. 单独使用

五位专家不一定要组成团队：

- 想要有据可查的稿子，让写作专家读线索包写稿，再交核验员；
- 只想检查已有稿子，把线索包和稿子交给核验员；
- 只想把定稿存进草稿箱，也要有核验报告，发布专员没通过核验不会发；
- 只想给已有文章配图、出预览 PDF，直接找推文配图专家。
